# Easy 모드 — 비전공자도 알아듣는 쉬운 해석판

`/pimp easy`로 호출되면 이 문서의 규칙이 normal 규칙(SKILL.md, analyst.md, designer.md, seminar-flow.md)의 **해당 부분을 덮어쓴다.**
여기서 언급하지 않은 규칙(충실성, 출처 표기, 파이프라인 순서, pptx QA)은 normal과 똑같이 지킨다.

## 목표

**청중**: 이 분야를 전공하지 않은 사람. 고등학교 수준의 상식은 있지만 이 분야 용어는 하나도 모른다고 가정한다.
발표가 끝났을 때 청중이 다음 네 가지를 **자기 말로** 설명할 수 있어야 한다.

1. 이 논문이 풀려는 문제가 무엇이고, 왜 중요한가
2. 기존 방법은 왜 부족했나
3. 이 논문은 무엇을 새로 했고, 그게 왜 통하나
4. 실제로 얼마나 좋아졌고, 그래서 결론이 무엇인가

쉽게 만든다는 것은 **내용을 덜어내는 것이 아니라 말을 바꾸는 것**이다.
논문의 흐름·핵심 논리·결론은 normal과 똑같이 전달하고, 표현만 비전공자의 언어로 옮긴다.

## 절대 빠지면 안 되는 것 (논리 사슬)

easy 덱의 액션 타이틀만 위에서 아래로 이어 읽었을 때, 아래 사슬이 **순서대로 모두** 나와야 한다. 하나라도 빠지면 easy 덱은 실패다.

```
문제(무엇을 풀려 하나) → 중요성(왜 풀어야 하나) → 기존 한계(왜 아직 못 풀었나)
→ 핵심 아이디어(무엇을 새로 했나) → 작동 방식(파이프라인의 모든 단계)
→ 검증(무엇으로 비교했나) → 메인 결과(대표 수치 포함) → 이유(Ablation: 무엇이 효과를 냈나)
→ 한계(저자 언급 + 리뷰어 관점) → 결론(Take-home)
```

- 방법의 **모든 구성요소**를 다룬다. 어렵다고 단계를 건너뛰지 않는다. 대신 수식 대신 말과 그림으로 설명한다.
- 메인 결과에는 **실제 수치**가 최소 1개 들어간다. "성능이 좋아졌다"로 뭉개지 않는다.
- 저자의 결론과 한계를 바꾸거나 과장하지 않는다. 쉬운 말로 옮기다가 주장의 강도가 세지면("항상", "완벽하게") 안 된다.

## 분량 — 조금 길어져도 되지만 너무 길어지면 안 된다

용어 풀이와 직관 설명 때문에 normal보다 조금 길어질 수 있다. 상한은 **같은 발표 시간의 normal 상한 + 3장**이다.

| 발표 시간 | normal 본문 | easy 본문 (간지 제외) |
|---|---|---|
| 10–15분 | 8–12 | 9–15 |
| 20–30분 | 15–24 | 18–27 |
| 40–60분 | 25–35 | 27–38 |

늘어난 장수는 **이해에 꼭 필요한 곳에만** 쓴다.
- 쓸 곳: 배경(비유로 여는 장 +1–2), 방법(구성요소 하나를 두 장으로 나누기 +1–2)
- 줄일 곳: 실험 설정은 1장으로 압축, 하이퍼파라미터·세부 수식·추가 실험은 Appendix로 보낸다
- Appendix는 최대 4장, 본문 장수에 넣지 않는다. 본문만 봐도 논리 사슬이 끊기지 않아야 한다.
- 상한을 넘을 것 같으면 장을 늘리지 말고 **덜 중요한 세부를 Appendix로 옮긴다.**

## 글 분량 — normal보다 더 적게

easy 슬라이드는 **글이 적고 그림이 많아야** 한다. 설명이 길어지면 화면이 아니라 발표자 노트로 보낸다.
아래 한도는 designer.md의 "텍스트 분량 한도"를 대신한다.

| 요소 | easy 한도 | (참고: normal) |
|---|---|---|
| 액션 타이틀 | ≤ 35자, 전문 용어 없이 | ≤ 40자 |
| 요점(pointsSlide) | 2–3개, head ≤ 20자, body ≤ 50자 | 2–4개, 25자 / 70자 |
| bullet (figure/compare) | 2–4개, 각 ≤ 35자 | 3–5개, 각 ≤ 45자 |
| TL;DR 칸 | 칸당 ≤ 60자 | ≤ 90자 |
| 표 | ≤ 5행 × 4열 | ≤ 8행 × 6열 |
| 수식 | 본문 슬라이드당 최대 1개, 덱 전체 본문에 최대 3개 (나머지는 Appendix) | 슬라이드당 1–2개 |
| 새 용어 | 슬라이드당 최대 2개 | — |
| 슬라이드 본문 전체 | 제목 제외 약 150자 이내 | — |

- 한 슬라이드 = 한 메시지 = 한 개념. 두 개념이 필요하면 장을 나누되, 위 분량 상한 안에서만 나눈다.
- 문장 대신 짧은 구(句)로 쓴다. "~하는 방법을 제안한다" ✗ → "새 방법: ~" ✓
- 글로 설명하던 것을 그림(processSlide, compareSlide, 논문 Figure)으로 바꿀 수 있으면 바꾼다.

## 쉬운 말 규칙

- **쉬운 우리말이 먼저, 원어는 뒤에 작게.** "주의 메커니즘(Attention)" ✗ → "중요한 부분에 집중하는 장치 (Attention)" ✓
  원어는 처음 등장할 때 한 번만 병기하고, 이후에는 쉬운 말만 쓴다. 모델명·데이터셋명은 이름 그대로 두되 무엇인지 한 번 풀어 준다.
- **용어는 등장하기 직전에 푼다.** 용어집을 앞에 몰아 두지 않는다. 필요한 순간에 한 줄 풀이를 붙인다.
- **비유는 한 개념에 하나.** 일상 경험(요리, 길 찾기, 시험 공부 등)에서 가져온다. 비유가 틀리게 만드는 부분이 있으면 노트에 "비유의 한계: …"를 한 줄 남긴다.
- **논문 원문 문장은 번역하지 말고 풀어 쓴다.** 직역투("~함으로써 ~를 달성한다")를 쓰지 않는다.
- **숫자는 의미와 함께.** "MSE 0.412 → 0.387"만 쓰지 말고 "오차가 줄었다(낮을수록 좋음)"처럼 방향과 뜻을 붙인다.
  퍼센트 개선 폭 같은 계산값은 brief에 "(계산값: …)"으로 적힌 것만 쓴다.
- **"왜?"를 생략하지 않는다.** 각 단계마다 "이게 왜 필요한가"를 한 줄로 답한다. 비전공자가 가장 먼저 길을 잃는 곳이 이유가 빠진 곳이다.

## 섹션별 조정 (seminar-flow.md 대비)

| 섹션 | easy에서 바꾸는 것 |
|---|---|
| TL;DR | Problem / Key Idea / Result를 비전공자 말로. Result에 대표 수치 1개 + 그 뜻 |
| 배경 지식 | 이 논문을 따라오는 데 꼭 필요한 개념만(최대 3개). 개념마다 비유 한 장면. normal보다 1–2장 더 써도 된다 |
| 문제 정의 & 동기 | "일상에서 이런 문제가 있다"로 시작해 논문의 문제로 연결. compareSlide로 기존 vs 제안을 대비 |
| 핵심 아이디어 | 개요 Figure + "한 문장으로 말하면" + 비유. 방법 세부 전에 반드시 큰 그림 |
| 방법 | 전체 파이프라인을 먼저(processSlide), 이후 구성요소별로 "무엇을 받아 → 무엇을 하고 → 무엇을 내놓나 → 왜 필요한가". 수식은 말로 먼저 설명하고, 꼭 필요한 것만 화면에 |
| 실험 설정 | 1장. "무엇과 비교했나 / 무엇으로 쟀나(높을수록·낮을수록 좋음)"만 |
| 메인 결과 | 표보다 statSlide·chartSlide 우선. 표를 쓰면 5행 × 4열 이내, 제안 기법 하이라이트 |
| Ablation | "이 부품을 빼 봤더니 → 이만큼 나빠졌다 → 그러니 이 부품이 핵심"의 3단 구조 그대로, 1–2장 |
| Critical Review | 1장. 강점 2개 / 한계 2개를 쉬운 말로. [저자 언급]·[리뷰어 관점] 라벨은 유지 |
| 결론 & Take-home | 3개, 각 한 문장. 비전공자가 집에 가서 말할 수 있는 문장으로 |
| 토론 질문 | 2–3개. 전문 지식 없이도 생각해 볼 수 있는 질문(응용, 사회적 의미, "만약 ~라면") |

## 수식·Figure·표 처리

- **수식**: 화면에는 "이 식이 말하는 것"을 한 문장으로 크게, 수식 이미지는 작게. 기호 표는 핵심 기호 3개 이내로 줄인다.
  본문 한도(덱 전체 3개)를 넘는 수식은 Appendix의 equationSlide로 보낸다.
- **Figure**: 논문 Figure를 쓸 때는 "어디를 봐야 하는지"를 화살표나 bullet 1–2개로 짚는다. 복잡한 Figure는 필요한 패널만 잘라 쓴다.
- **표**: 비교 대상은 대표 2–3개만 남긴다(제안 기법, 가장 강한 기존 기법, 필요하면 가장 기본적인 기법). 나머지는 Appendix.

## Analyst 추가 작업 — brief §13

easy 모드일 때 Analyst는 normal brief(§0–§12)를 **그대로 다 쓴 뒤** 아래 §13을 추가한다.
normal 절을 쉬운 말로 고쳐 쓰지 않는다 — 정확한 원본(§0–§12)과 쉬운 해석(§13)을 분리해야 Designer가 쉬운 말로 옮기다가 사실을 바꾸지 않는다.
§13의 모든 문장은 §0–§12의 어느 항목을 풀어 쓴 것인지 `(→ §5.2)`처럼 표시한다.

```markdown
## 13. 쉬운 설명 (easy 모드 전용)

### 13.1 논리 사슬 (비전공자 말로, 각 1–2문장)
- 문제: <...> (→ §3)
- 왜 중요한가: <...> (→ §3)
- 기존 방법의 한계: <...> (→ §3)
- 핵심 아이디어: <...> (→ §4)
- 작동 방식: <파이프라인 각 단계를 한 줄씩> (→ §5.0)
- 결과: <대표 수치 + 그 뜻> (→ §6.2)
- 왜 효과가 있나: <...> (→ §6.3)
- 한계: <...> (→ §7)
- 결론: <...> (→ §9)

### 13.2 용어 쉬운 풀이
발표에 등장하는 전문 용어 전부. 처음 등장하는 슬라이드 순서대로.
| 용어 (원어) | 쉬운 말 | 한 줄 풀이 (전공 지식 없이) | 비유 (있으면) |
|---|---|---|---|

### 13.3 비유 모음
| 개념 | 비유 | 비유가 맞는 부분 | 비유의 한계 |
|---|---|---|---|

### 13.4 수식 풀이
§5의 핵심 수식마다: Eq. 번호 → "이 식이 말하는 것" 한 문장 (수학 기호 없이)

### 13.5 숫자 읽는 법
| 지표 | 무엇을 재나 (쉬운 말) | 높을수록/낮을수록 좋음 | 대표 결과를 쉬운 말로 |
|---|---|---|---|
```

Analyst 자기 점검에 추가:
- [ ] §13.1 논리 사슬이 §1–§9와 모순 없이 대응하고, 빠진 고리가 없다.
- [ ] §13의 모든 풀이에 `(→ §N)` 역참조가 있다. §0–§12에 없는 사실을 새로 넣지 않았다.
- [ ] 쉬운 말로 바꾸면서 주장이 과장되거나 약해지지 않았다.

## 발표자 노트 (easy)

- 노트가 화면의 부족한 설명을 채운다. 슬라이드당 150–400자 유지, 용어 풀이와 비유는 노트에서 말로 한 번 더 풀어 준다.
- 첫 문장은 "이 장에서 알아야 할 것 한 가지"로 시작한다.
- 비유를 쓴 장에는 "비유의 한계: …"를 마지막 줄에 적어, 질문을 받았을 때 발표자가 정확한 설명으로 돌아갈 수 있게 한다.

## Easy 품질 체크리스트 (designer.md 체크리스트에 추가)

- [ ] 액션 타이틀만 이어 읽으면 "절대 빠지면 안 되는 것"의 논리 사슬이 순서대로 모두 나온다.
- [ ] 방법의 모든 구성요소가 본문에 있다(Appendix로만 빠진 구성요소가 없다).
- [ ] 본문 장수가 easy 분량 표 상한 이내다. 상한을 넘으면 세부를 Appendix로 옮겼다.
- [ ] 모든 슬라이드가 easy 글 분량 한도 이내다. 넘친 설명은 노트로 옮겼다.
- [ ] 액션 타이틀에 풀이 없는 전문 용어가 없다. 모든 용어는 처음 등장할 때 풀이가 붙어 있다.
- [ ] 모든 수치가 brief §0–§12와 일치하고, 방향(좋아짐/나빠짐)과 뜻이 함께 적혀 있다.
- [ ] 비전공자 입장에서 한 번 읽어 봤을 때 "이건 뭐지?" 하고 막히는 장이 없다.
